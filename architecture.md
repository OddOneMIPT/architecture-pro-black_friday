## Задание 7. Проектирование схем коллекций для шардирования

### Коллекция `orders` (заказы)

**Схема:**

```js
{
  "_id": ObjectId,
  "order_id": String,           // уникальный идентификатор заказа
  "customer_id": ObjectId,      // идентификатор клиента
  "created_at": ISODate,        // дата и время оформления заказа
  "items": [
    {
      "product_id": ObjectId,
      "price": NumberDecimal
    }
  ],
  "status": String,             // "pending" | "processing" | "shipped" | "delivered" | "cancelled"
  "total_amount": NumberDecimal,
  "geo_zone": String            // "Moscow" | "Ekaterinburg" | "Kaliningrad" | ...
}
```

**Ключ шардирования:** `{ customer_id: "hashed" }`

**Обоснование:**
- Основной паттерн запросов — «история заказов конкретного пользователя». Размещение всех заказов одного клиента на одном шарде устраняет scatter-gather при чтении истории.
- Хешированное шардирование обеспечивает равномерное распределение независимо от паттернов значений `customer_id`.
- Вариант `geo_zone` был отклонён: популярные геозоны (например, Москва) создали бы горячие шарды.

**Команда MongoDB:**
```js
sh.shardCollection("somedb.orders", { "customer_id": "hashed" });
```

### Коллекция `products` (товары)

**Схема:**

```js
{
  "_id": ObjectId,
  "product_id": String,         // уникальный идентификатор товара
  "name": String,
  "category": String,           // "Электроника" | "Аудио" | "Аксессуары" | ...
  "price": NumberDecimal,
  "inventory": {
    "<geo_zone>": NumberInt     // например: "Moscow": 50, "Ekaterinburg": 30
  },
  "attributes": {
    "color": String,
    "size": String
  }
}
```

**Ключ шардирования:** `{ _id: "hashed" }`

**Обоснование:**
- Основная операция — просмотр страницы товара по `_id`. Хеширование по `_id` равномерно распределяет нагрузку.
- Вариант `category` был отклонён: на категорию «Электроника» приходится 70% трафика, что неизбежно перегрузит один шард.
- Поиск по категориям и фильтрация по цене работают в режиме scatter-gather, что приемлемо для каталога с высокой долей чтения.

**Команда MongoDB:**
```js
sh.shardCollection("somedb.products", { "_id": "hashed" });
```

### Коллекция `carts` (корзины)

**Схема:**

```js
{
  "_id": ObjectId,
  "user_id": ObjectId,          // null для гостевых корзин
  "session_id": String,         // всегда задан (и для гостей, и для авторизованных пользователей)
  "items": [
    {
      "product_id": ObjectId,
      "quantity": NumberInt
    }
  ],
  "status": String,             // "active" | "ordered" | "abandoned"
  "created_at": ISODate,
  "updated_at": ISODate,
  "expires_at": ISODate         // TTL-индекс для автоматической очистки
}
```

**TTL-индекс для автоматической очистки:**
```js
db.carts.createIndex({ "expires_at": 1 }, { expireAfterSeconds: 0 });
```

**Ключ шардирования:** `{ session_id: "hashed" }`

**Обоснование:**
- `session_id` всегда присутствует как для гостей, так и для авторизованных пользователей — универсальный ключ доступа.
- Хешированное шардирование равномерно распределяет сессии по шардам.
- Вариант `user_id` был отклонён: для всех гостевых корзин `user_id` равен `null`, что разместило бы их все на одном шарде.

**Команда MongoDB:**
```js
sh.shardCollection("somedb.carts", { "session_id": "hashed" });
```

**Порог определения горячего шарда:**
Шард считается «горячим», если на нём хранится на 33% больше данных или обрабатывается на 40% больше операций, чем в среднем по кластеру.

### Механизмы автоматического перераспределения данных

**1. Встроенный балансировщик MongoDB (основной механизм):**
```js
// Проверить состояние балансировщика
sh.getBalancerState()

// Запустить балансировщик
sh.startBalancer()

// Настроить окно работы балансировщика (в ночные часы)
use config
db.settings.updateOne(
  { _id: "balancer" },
  { $set: { activeWindow: { start: "02:00", stop: "06:00" } } },
  { upsert: true }
)
```

**2. Зональное шардирование для географического распределения:**
```js
// Назначить шард в зону
sh.addShardToZone("shard1", "zone-central")
sh.addShardToZone("shard2", "zone-ural")

// Закрепить диапазон ключей за зоной
sh.updateZoneKeyRange(
  "somedb.orders",
  { geo_zone: "Moscow" },
  { geo_zone: "N" },
  "zone-central"
)
```

**3. Уточнение ключа шардирования (MongoDB 4.4+):**
```js
// Добавить более селективный суффикс к ключу шардирования
db.adminCommand({
  refineCollectionShardKey: "somedb.products",
  key: { _id: "hashed", category: 1 }
})
```

**Действия при обнаружении горячего шарда:**
1. Убедиться, что балансировщик запущен и не ограничен по времени работы.
2. При медленной работе балансировщика — вручную разбить крупные чанки: `sh.splitAt("somedb.products", { _id: <midpoint> })`.
3. Перенести конкретный чанк на менее нагруженный шард: `db.adminCommand({ moveChunk: "somedb.products", find: { _id: <key> }, to: "shard2" })`.
4. Если горячий шард — следствие неудачного ключа шардирования, уточнить ключ или перешардировать коллекцию.

## Задание 9. Настройка чтения с реплик и консистентность

### Таблица настроек чтения

| Коллекция | Операция | Реплика | Обоснование |
|---|---|---|---|
| `products` | Просмотр каталога, список по категориям | secondary | Небольшое отставание (секунды) приемлемо для каталога |
| `products` | Страница товара | secondary | Незначительно устаревшие цена/описание допустимы |
| `products` | Проверка остатка перед покупкой | primary | Должно быть точным: устаревшие данные — риск продажи недоступного товара |
| `orders` | История заказов пользователя | secondary | Пользователи допускают небольшую задержку в истории |
| `orders` | Текущий статус заказа | primary | Пользователь ожидает актуальный статус (например, «Отправлен») |
| `orders` | Создание / обновление заказа | primary | Требуется согласованность записи |
| `carts` | Загрузка текущей корзины | primary | Корзина должна отражать последнее состояние; возможны параллельные изменения |
| `carts` | Все операции изменения корзины | primary | Критична согласованность; потеря данных = потеря покупки |

### Допустимая задержка репликации

| Коллекция | Операция | Допустимое отставание |
|---|---|---|
| `products` | Просмотр каталога | до 30 секунд |
| `products` | Проверка остатка перед покупкой | 0 (только primary) |
| `orders` | История заказов | до 60 секунд |
| `orders` | Текущий статус заказа | 0 (только primary) |

## Задание 10. Миграция на Cassandra: модель данных, стратегии репликации и шардирования

### 10.1 Какие данные переносить в Cassandra

**Подходящие кандидаты:**

| Сущность | Обоснование |
|---|---|
| `carts` (корзины) | Высокая интенсивность записи, простой доступ по ключу, нативный TTL, нет сложных джойнов |
| `user_sessions` (сессии) | Экстремальная пропускная способность, простой поиск по `session_id`, TTL, write-heavy |
| `order_history` (история заказов, денормализованная) | Паттерн временного ряда, высокая читаемость, партиция по `customer_id` + timestamp естественна |

**Оставить в MongoDB:**

| Сущность | Обоснование |
|---|---|
| `products` (каталог) | Требует сложной фильтрации (категория + ценовой диапазон + геозонный инвентарь), аналитики |
| `orders` (транзакционные) | Сложные многопольные запросы, переходы статусов, аналитика |

**Обоснование выбора Cassandra:**
- Cassandra использует consistent hashing с виртуальными узлами (vnodes) — добавление нового узла требует перераспределения только части данных, без полного решардинга. Именно это устраняет просадку latency, которая возникала в MongoDB при добавлении шардов в пик нагрузки.
- Leaderless-репликация: нет единой точки отказа и выборов primary, что критично при нагрузке 50 000 RPS.
- Путь записи O(1) независимо от размера кластера.

### 10.2 Модель данных и ключи партиционирования

#### Таблица `carts`

```cql
CREATE TABLE carts (
    session_id  text,
    user_id     uuid,
    status      text,
    items       text,           -- JSON-сериализованный список {product_id, quantity}
    created_at  timestamp,
    updated_at  timestamp,
    expires_at  timestamp,
    PRIMARY KEY (session_id)
) WITH default_time_to_live = 604800;  -- 7 дней
```

- **Ключ партиции:** `session_id` — всегда присутствует как для гостей, так и для авторизованных пользователей; высокая кардинальность обеспечивает равномерное распределение.
- **Риск горячей партиции:** низкий — session ID имеет UUID-подобную структуру.
- **Влияние решардинга:** минимальное — добавление vnodes перераспределяет только новые токены.

#### Таблица `orders_by_customer`

```cql
CREATE TABLE orders_by_customer (
    customer_id  uuid,
    created_at   timestamp,
    order_id     uuid,
    status       text,
    total_amount decimal,
    geo_zone     text,
    items        text,          -- JSON-сериализованный список товаров
    PRIMARY KEY (customer_id, created_at)
) WITH CLUSTERING ORDER BY (created_at DESC);
```

- **Ключ партиции:** `customer_id` — группирует все заказы одного пользователя в одной партиции, что обеспечивает эффективный скан истории.
- **Кластерный ключ:** `created_at DESC` — последние заказы первыми, соответствует порядку отображения в UI.
- **Риск горячей партиции:** низкий–средний. Пользователь с тысячами заказов создаёт широкую партицию, но не непропорциональную нагрузку. Контролируется через `nodetool tablestats`.
- **При обнаружении горячей партиции:** добавить bucket к ключу: `PRIMARY KEY ((customer_id, year_month), created_at)`.

#### Таблица `user_sessions`

```cql
CREATE TABLE user_sessions (
    session_id  text  PRIMARY KEY,
    user_id     uuid,
    created_at  timestamp,
    expires_at  timestamp
) WITH default_time_to_live = 86400;  -- 24 часа
```

- **Ключ партиции:** `session_id` — случайный токен, идеально равномерное распределение.

### 10.3 Стратегии обеспечения целостности данных

#### Hinted Handoff

**Что делает:** когда реплика временно недоступна, координатор сохраняет запись как «подсказку» (hint) и воспроизводит её после восстановления узла.

**Применять для:** всех сущностей (`carts`, `orders_by_customer`, `user_sessions`).

**Обоснование:** обрабатывает плановые перезагрузки узлов, rolling-обновления и кратковременные сетевые сбои без блокировки записи. В Чёрную пятницу трафик не может ждать восстановления узла.

**Настройка:**
```yaml
# cassandra.yaml
hinted_handoff_enabled: true
max_hint_window_in_ms: 10800000  # 3 часа
```

#### Read Repair

**Что делает:** при чтении с уровнем согласованности > ONE Cassandra сравнивает реплики и асинхронно восстанавливает расхождения.

**Применять для:** `carts`, `orders_by_customer` — сущности, где устаревшие данные могут привести к бизнес-потерям (конфликт корзины, неверный статус заказа).

**Не критично для:** `user_sessions` — сессии эфемерны, устаревшая сессия просто потребует повторного входа.

**Настройка:**
```cql
ALTER TABLE carts WITH read_repair_chance = 0.1;              -- 10% запросов инициируют синхронное восстановление
ALTER TABLE orders_by_customer WITH read_repair_chance = 0.1;
ALTER TABLE user_sessions WITH read_repair_chance = 0.0;      -- не требуется
```

#### Anti-Entropy Repair

**Что делает:** полное сравнение деревьев Меркля по всем репликам и восстановление любых расхождений, включая случаи, когда Hinted Handoff уже истёк.

**Применять для:** всех сущностей — по расписанию раз в неделю в нерабочие часы.

**Обоснование:** обеспечивает долгосрочную согласованность данных, устраняет дрейф, который мог миновать Hinted Handoff (например, узел был недоступен дольше окна хранения подсказок).

**Команда:**
```bash
# Восстановление конкретного keyspace на узле
nodetool repair -full mobile_world

# Планировщик (cron) — еженедельно, ночью
0 3 * * 0 nodetool repair -full mobile_world
```

### Рекомендации по уровням согласованности

| Сущность | Запись (Write CL) | Чтение (Read CL) | Компромисс |
|---|---|---|---|
| `carts` | `QUORUM` | `LOCAL_QUORUM` | Баланс: надёжность записи и актуальность чтения |
| `orders_by_customer` | `QUORUM` | `ONE` | Заказы append-only; quorum при записи гарантирует сохранность; чтение допускает небольшое отставание |
| `user_sessions` | `ONE` | `ONE` | Максимальная скорость; сессии эфемерны и легко воссоздаются |
